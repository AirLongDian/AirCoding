# 无人值守分析方案评估（2026-10-28）

## 结论

Understand 产品能力并不天然要求每次人工操作：Jenkins 插件源码已证明存在从编译数据库创建项目、分析的 CLI 链路。之前的手工建库只是验证包的缺口，已补自动脚本。不能把这项源码证据等同于 Understand 8.0 Build 1266、当前个人授权与管理员策略已经实测通过。

云端开放工具链已验证预装依赖后的非交互批处理，包括关系变更、失败结果不发布和旧结果版本校验。Understand 实例仍不可用，未将此项标成验证通过。Joern 可自动运行，但已有特定语法导致调用关系缺失的复现。

## 开放工具链实验

前置为云端已经准备好的 GNU C++、CMake、clang-uml 0.6.3、scip-clang 0.4.1 与 Python protobuf 依赖。所有子进程 stdin=DEVNULL，无人点击、无 GUI、无模型推理。

1. 从空构建目录自动配置、编译并运行样例，生成 CMake File API、SCIP 和 clang-uml JSON；确认跨层业务引用存在。
2. 输入未变，选用先前有效产物，不重跑分析。
3. 删除业务调用、头文件/实现与 policy target，重新配置/编译/分析；文档由 10 变 8，policy target 与对应业务引用消失。
4. 注入无法编译的源码，构建失败；没有发布新分析结果，旧的有效文件保持可恢复，但按当前源码版本查询时被拒绝，不能当作最新结果。
5. 恢复先前源码/配置，选择与该输入版本相同的已验证产物。

首轮和变更轮各约 1.7 秒，仅为本夹具和此机器上的单次测量，不推断大型项目性能。这里是变更后全量重新索引，未证明前端增量分析能力。当前源码在分析期间未被外部并发修改，未验证分布式发布、崩溃恢复或常驻 MCP 竞争。

原始实验结果见 reference-results/unattended-summary.json。

## Understand 的可执行自动验证入口

新增 run_understand.py：

```text
python run_understand.py --und "实际的und路径" --upython "实际的upython路径"
```

在安装、授权和工具链预先配置完成后，启动一次即可自动执行：API 预检 → CMake 配置/编译/运行 → CLI 建库分析 → Python API 导出 → 两种写法证据对照。

CLI 形态依据：

```text
und -db PROJECT.und create -languages all add compile_commands.json analyze
```

来源：https://github.com/stinb/understand-jenkins-plugin/blob/master/src/main/java/io/jenkins/plugins/understand/UndBuilder.java

脚本关闭输入，配置超时，保留失败日志，不启用内置 AI、不修改管理员策略、不配置或收集授权。其 --help 已执行，实际 Analyze/API 路径未执行；这不计作 Understand 测试通过。当前授权或管理策略是否允许此路径，需要合法安装环境实际确认。

这条批量 API 路径不依赖 GUI MCP 开关；但不能据此承诺其他管理策略绝不会限制 CLI/Python，未进行任何策略绕过。

## 部署约束

无人值守不等于无需部署。任何分析引擎都需要一个已配置的执行节点。

- 若 Understand 在常驻节点上安装并合法激活，技术上有非交互链路可验证。
- 若只有用户个人电脑可用，关机、休眠、失联会让分析不可用；脚本不能消除该约束。
- 若构建和任务都在云端，而 Understand 无法在同一云端或可达的常驻节点运行，不能把它当作必需依赖。

## 建议（待用户决定，尚未修改项目选型或应用代码）
